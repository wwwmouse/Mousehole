# mousehole — 产品定义与开发指南

**版本：** 0.1  
**状态：** 初始产品定义  
**项目名称：** mousehole  
**产品类别：** 个人 AI 工作空间  
**文档用途：** 产品定位、核心设计原则、功能边界，以及面向开发智能体的指导。

---

# 1. 产品概述

## 1.1 产品愿景

mousehole 是一个个人 AI 工作空间，旨在帮助用户整理信息、管理项目、执行任务、产出可复用的成果物，并协调不同的 AI 能力与外部工具。

它并不打算成为又一个基于对话的 AI 助手，或一个简单的 Agent 封装。

相反，mousehole 希望提供一个持久的工作环境，让用户能够持续积累知识、组织工作、管理可复用的 AI 能力，并与 AI 协作完成日益复杂的任务。

长期愿景是构建一个个人 AI 工作环境，随着项目、知识、工作流、技能与执行历史的积累，它变得越来越有用。

**核心定位：**

> mousehole 是一个个人 AI 工作空间，用于组织工作、管理知识、协调 AI 能力与外部工具，并帮助用户持续产出与积累有价值的工作成果物。

## 1.2 核心价值主张

mousehole 应提供三项基础能力：

### 1. 工作组织

组织用户的工作环境：

- 工作空间与项目
- 任务与执行历史
- 文档与知识
- 生成的成果物
- 可复用的能力

用户不应在每次开始新任务时都需要重建自己的工作上下文。

### 2. AI 协作

AI 应理解用户的目标与相关的工作上下文，选择合适的能力，并帮助完成任务。

不同任务应使用不同的执行策略。

简单的信息检索不需要 Agent。复杂任务可能需要规划、工具调用、工作流或自主执行。

### 3. 工具协调

mousehole 应能独立运行，同时对外部工具保持开放。

它应提供有用的原生能力，但避免不必要地重建专业软件。

外部工具、服务、API、IDE 及其他 Agent 系统应被视为 mousehole 能力的延伸。

**核心原则：**

> mousehole 不必亲自完成每一个操作，但它应组织工作、理解其上下文、协调执行，并留存结果。

# 2. 产品设计原则

以下原则应指导产品决策与实现。

## 2.1 工作空间优先，而非对话优先

主要交互模型应是一个持久的工作空间，而不是一次孤立的对话。

对话是一种交互方式，而不是核心组织概念。

用户应能独立于单次对话来管理项目、任务、文件、成果物与能力。

## 2.2 独立性与开放性

mousehole 必须在不依赖外部 Agent 产品的情况下提供有意义的功能。

同时，它应支持集成，而不是重复构建已有的专业工具。

示例：

- 原生文档处理，而非需要外部文档 Agent。
- 外部 IDE 集成，而非重建一个完整的 IDE。
- MCP 集成以接入外部工具。
- 可选地集成专业编码 Agent。

## 2.3 连续性

工作应超越单次对话而持久存在。

一个已完成的任务应留下可复用的结果、执行记录与相关上下文。

新任务应能够引用之前的工作，而不是从零开始。

## 2.4 用户控制

用户应能够查看、定制、批准与中断 AI 的操作。

高风险操作必须要求明确的人类参与（Human-in-the-Loop，HITL）批准。

AI 的自主性应逐步引入，而非默认假定。

## 2.5 可扩展性

系统应支持用户创建与从外部导入的：

- 提示词（Prompts）
- 技能（Skills）
- 工作流（Workflows）
- 工具与集成

能力系统应保持开放与模块化。

## 2.6 长期可维护性

避免不必要的复杂性与过早引入框架。

优先选择清晰的模块边界、可复用的接口、可测试性与易于理解的架构。

# 3. 目标用户与使用场景

## 3.1 初始目标用户

初始目标是想用 AI 来组织并完成各类工作的个人用户。

产品应优先关注个人生产力，而非企业管理或多租户管理。

潜在用户可能包括：

- 学生与研究人员
- 开发者与技术从业者
- 同时管理多个项目的个人
- 经常处理文档、数据与技术知识的用户
- 希望构建并复用自己 AI 工作流的用户

初始产品应能作为开发者自己的个人工作环境而有用，同时保留服务更广泛受众的潜力。

## 3.2 代表性场景

### 信息检索

- 搜索并理解上传的文档。
- 从个人知识中检索信息。
- 总结技术材料。

### 知识管理

- 组织文档。
- 构建可检索的知识集合。
- 将文件关联到项目。
- 复用先前的研究与分析。

### 生产力

- 处理结构化数据。
- 生成报告。
- 将信息转化为文档。
- 整理学习笔记与研究成果。

### 工程辅助

- 分析软件仓库。
- 理解项目架构。
- 检查依赖关系与代码结构。
- 生成技术文档。
- 与外部编码工具协作。

### 复杂任务执行

- 分解复杂目标。
- 选择合适的技能（Skills）与工作流（Workflows）。
- 调用工具与外部服务。
- 在必要时请求用户批准。
- 验证结果并产出交付物。

这些场景代表预期的能力范围，并不要求在初始版本中实现每一项功能。

# 4. 核心产品结构

初始概念结构为：

**工作空间（Workspace）→ 项目（Project）→ 任务（Task）→ 执行（Execution）**

文件、成果物、对话与能力均与此结构相关联。

## 4.1 工作空间（Workspace）

工作空间代表一个持久的工作环境。

它为用户的日常工作提供上下文与组织方式。

规划了两种初始工作空间模式：

### 全局工作空间（Global Workspace）

用于：

- 临时任务
- 通用信息检索
- 跨项目任务
- 不属于特定项目的个人活动

### 项目工作空间（Project Workspace）

用于需要持久上下文的长期项目。

示例：

- 软件开发项目
- 研究项目
- 学习项目
- 竞赛项目

并非每个任务都需要专属项目。

用户应能直接在全局工作空间中开始临时任务，仅在必要时创建或关联项目。

## 4.2 项目（Project）

项目是工作空间内的长期组织单元。

它可以包含：

- 项目专属上下文
- 相关文件与知识引用
- 任务
- 成果物
- 对话
- 项目专属能力
- 执行历史

项目应保持多个任务之间的连续性。

## 4.3 任务（Task）

任务代表用户想要完成的特定目标。

示例：

- 分析一个软件架构。
- 总结一份技术文档。
- 对比两个数据集。
- 生成一份项目报告。

任务不等同于对话。

任务应具有明确的目标、相关上下文、关联能力与最终结果。

一个任务可以有多次执行。

## 4.4 执行（Execution）

执行代表为完成某个任务而进行的一次实际尝试。

它应留存相关信息，例如：

- 执行状态
- 所选能力
- 执行步骤
- 工具调用
- 日志
- 错误
- 审批请求
- 最终结果

任务与执行之间的区分很重要。

例如，若一次分析失败、用户更改了执行配置，系统应能在同一任务下执行另一次运行。

## 4.5 文件（File）

文件代表用户提供的原始材料。

初始设计倾向采用统一的全局库（Global Library）。

文件不必仅归属于某一个项目。

同一个文件可以被多个项目或任务引用。

文件的存储位置与其被使用的范围应是两个分离的概念。

## 4.6 成果物（Artifact）

成果物是通过工作生成或维护的可复用产出。

示例：

- 报告
- 技术文档
- 数据分析结果
- 架构图
- 研究总结
- 生成的文件

成果物不应只以对话中的消息形式存在。

它们应可被独立访问、关联到相关项目或任务，并在未来工作中可复用。

## 4.7 对话（Conversation）

对话是用户与 AI 之间的交互记录。

它们可以与任务、项目或工作空间相关联。

对话历史应支持连续性，但不应成为有意义工作成果的唯一存储机制。

# 5. 工作空间与信息架构

## 5.1 初始首页方向

首页应结合：

- 结构化的工作空间仪表盘。
- 显著的任务创建入口。
- 最近使用的项目。
- 最近的任务与成果物。
- 快速访问全局库与能力库。

首页应给人个人工作仪表盘的感觉。

用户应能立即开始工作，同时对已有项目与活动保持清晰的理解。

设计应优先考虑清晰度与方位感，而不是尽可能减少每一次点击。

少量刻意的导航步骤，胜过让用户不确定自己身在何处的界面。

## 5.2 工作空间内部布局

工作空间的最终内部布局尚未确定。

持久侧边栏、项目导航、任务列表、成果物区域与 AI 交互面板都是可能的方向。

不要过早假定每个工作空间都必须采用以对话为中心的布局。

内部布局应通过进一步的产品与交互设计确定。

## 5.3 统一库与上下文边界

全局库应提供统一的文件管理。

然而，将文件上传至全局库，不应自动意味着每个任务都能访问每个文件。

任务上下文应是显式且可控的。

系统应支持：

- 全局文件存储。
- 项目专属文件引用。
- 任务专属文件选择。
- 可选的跨项目检索。
- 清晰可见地展示某个任务正在使用哪些文件。

避免不必要的文件重复。

# 6. 能力库

能力库是 mousehole 的核心产品差异化之一。

它让用户能够积累、定制、导入并复用自己的 AI 工作方法。

系统应区分四种能力类型。

## 6.1 提示词（Prompts）

提示词定义指令、角色、约束与输出期望。

示例：

- 技术文档分析提示词。
- 代码审查提示词。
- 学术论文总结提示词。
- 报告生成模板。

## 6.2 技能（Skills）

技能封装可复用的专项能力。

它们可以包含指令、资源、脚本与执行要求。

示例：

- PDF 文档处理。
- 仓库结构分析。
- 技术文档抽取。
- 数据集检查。

## 6.3 工作流（Workflows）

工作流将多个步骤与能力组织为可重复的流程。

示例：

技术项目分析工作流：

1. 检查项目结构。
2. 分析依赖关系。
3. 识别主要组件。
4. 检查重要的实现细节。
5. 生成架构报告。

工作流应支持可预期的执行与可复用的流程。

## 6.4 工具（Tools）

工具提供具体的执行能力。

示例：

- 文件操作
- 数据库查询
- API 请求
- 数据处理
- 外部服务集成

提示词、技能、工作流与工具应保持为彼此不同的概念，尽管它们可以组合使用。

## 6.5 能力选择

初始默认行为应采用基于推荐的模式。

当用户创建任务时：

1. AI 分析目标与上下文。
2. AI 推荐合适的提示词、技能与工作流。
3. 用户可以查看并确认选择。
4. 任务使用所选能力继续执行。

同时也必须支持手动选择。

用户应能显式选择、排除或定制能力。

后期可以引入更自主的能力选择模式。

## 6.6 能力创建

长期应支持三种创建方式：

### AI 辅助创建

用户描述自己的需求，AI 生成初始的能力定义。

用户可以审阅、编辑、测试并保存它。

### 基于任务的抽取

一次成功的执行可以被审阅并转换为可复用的技能或工作流。

这应是一个由用户显式控制的流程，而不是不受控的自动修改。

### 手动创建与编辑

用户必须保留直接创建与修改能力的能力。

这一点很重要，因为用户可能已经拥有来自外部的成熟提示词、技能与工作流。

## 6.7 外部能力导入

系统应支持导入外部能力，尤其是来自 GitHub 及兼容生态的能力。

导入的能力应是可管理的资产，而不是无人跟踪的文件。

重要考量：

- 来源与作者信息
- 版本信息
- 许可信息（如有）
- 依赖项
- 所需权限
- 安全检查
- 手动修改
- 测试与调试
- 启用/禁用控制
- 更新比对与回滚

导入的指令与脚本必须被视为不可信输入。

导入一个技能，不得自动授予其对文件、工具或外部服务的无限制访问权。

# 7. AI 执行与 Agent 架构

## 7.1 总体原则

mousehole 不应对每个任务都使用 Agent。

执行策略应取决于任务的复杂度与要求。

可能的执行方式包括：

- 直接与模型交互
- 基于检索的处理
- 单步工具执行
- 确定性工作流
- 基于 Agent 的规划与执行
- 委托外部 Agent

系统应使用能满足任务的最简可靠方式。

## 7.2 任务执行生命周期

一个概念性的执行生命周期：

1. 接收用户的目标。
2. 识别目标工作空间或项目。
3. 收集相关上下文。
4. 分析任务。
5. 推荐合适的能力。
6. 在需要时获得用户确认。
7. 在必要时规划执行。
8. 执行任务。
9. 为受保护操作请求批准。
10. 验证结果。
11. 产出并保存成果物。
12. 记录执行历史。

这是一个概念性流程，不是最终确定的实现规范。

## 7.3 人类参与（Human-in-the-Loop）

高风险操作必须要求用户显式批准。

包括以下这类操作：

- 删除或覆盖重要文件。
- 执行可能具有破坏性的命令。
- 修改受保护的项目资源。
- 对外发布信息。
- 通过外部服务执行具有后果性影响的操作。

HITL 必须在执行与权限层强制执行。

不要仅依赖提示词指令来阻止危险操作。

系统应通过展示以下内容，使审批请求易于理解：

- 将执行什么操作。
- 影响哪些资源。
- 可能产生什么后果。
- 该操作是否可逆。

## 7.4 执行可观测性

用户应能查看重要的执行信息。

示例：

- 当前执行状态。
- 所选能力。
- 工具调用。
- 相关输入与输出。
- 审批历史。
- 错误与重试。
- 最终成果物。

系统的行为不应像一个不透明的黑盒。

# 8. 数据隐私与部署策略

## 8.1 本地优先

首选部署策略是本地优先（Local-first）。

应用、数据库与用户管理的文件应主要位于用户的本地环境或自管理基础设施中。

系统应支持便捷的本地部署，Docker Compose 可作为初始部署方式。

## 8.2 云端模型作为主要模型策略

通过 API 密钥连接的云端模型应作为主要的模型集成方式。

这反映了用户当前访问 Agent 能力的常见方式，并能在无需本地推理硬件的情况下使用更强的模型。

系统应通过统一的模型接口支持多个模型提供商。

API 密钥及其他凭据必须安全存储，不得暴露在前端代码或普通日志中。

## 8.3 本地模型作为可选扩展

通过 Ollama 等服务进行本地推理可作为可选扩展予以支持。

但本地模型部署并非默认的产品假设。

初始产品不应要求用户安装或维护本地推理基础设施。

## 8.4 数据传输透明性

本地部署并不自动意味着所有数据都留在本地。

当使用云端模型或外部服务时，相关数据可能离开本地环境。

系统应：

- 清晰标明何时使用了外部服务。
- 使所用模型与提供商可见。
- 避免静默传输不必要的数据。
- 提供可配置的外部服务权限。
- 在实质性影响隐私时，说明发送了哪些信息。

长期目标是让用户掌控本地数据与外部服务之间的边界。

# 9. 外部集成

mousehole 应对外部工具与生态保持开放。

潜在集成包括：

- MCP 服务器
- 本地文件系统
- Git 与 GitHub
- IDE 与编码 Agent
- 数据库
- 外部 API
- 文档与数据处理工具

系统应优先集成，而非重新实现。

不过，集成必须依据用户的实际需求引入，而不是仅仅为了增加功能数量而添加。

外部集成应具有清晰的权限边界与执行记录。

# 10. 参考项目：AgentOne

参考仓库：

https://github.com/sangshy-go/AgentOne

AgentOne 是一个重要的工程参考，因为它的功能与若干计划中的 mousehole 能力有重叠。

值得研究的方向：

- 模型集成与配置
- RAG 与知识库管理
- ReAct Agent 运行时
- 技能生态
- MCP 集成
- 工具执行
- 权限确认
- 日志与可观测性
- 基于 Docker 的部署

AgentOne 应被视为工程参考，而不是要照抄的产品蓝图。

产品差异在于：

- AgentOne 主要关注配置、管理与运行 AI Agent。
- mousehole 主要关注组织持久的个人工作，并利用 AI 能力完成这些工作。

mousehole 可以复用相似的工程概念，但其导航、信息架构与数据模型应围绕工作空间、项目、任务、执行、成果物与能力来设计。

除非确有必要，避免复刻面向企业的功能。

# 11. 开发策略与范围控制

## 11.1 避免过早复杂化

不要在初始版本中试图实现全部长期愿景。

不要仅因为某种技术属于现代 Agent 系统，就引入复杂技术。

初始版本中不应作为必需功能的示例：

- 多 Agent 编排
- 复杂的自主规划
- 大规模企业级 RBAC
- 技能市场
- 高级分布式执行
- 完整的 IDE 替代
- 完全自主的能力演化

首要目标是打造一个可靠、可理解的个人工作空间。

## 11.2 建议的开发方向

以下是暂定推进顺序，并非最终确定的排期。

### 基础

- 应用结构
- 基础的工作空间与项目管理
- 模型提供商配置
- 全局库
- 基础的任务管理

### 核心生产力

- 文档处理
- 知识检索
- AI 辅助的任务执行
- 成果物管理
- 执行历史

### 能力系统

# 12. 开发智能体指令

本节尤为重要。

任何参与 mousehole 开发的 AI 编码 Agent 都必须遵循以下规则。

## 12.1 不要把项目当作通用聊天机器人

不要把 mousehole 简化为：

- 一个带 RAG 的聊天界面。
- 一个带工具调用的聊天界面。
- 一组 Agent 配置页面。
- 对某个外部 Agent API 的薄封装。

每一项重大设计决策都应依据"工作空间优先"的产品愿景来评估。

## 12.2 保持产品模型

尊重以下概念之间的区分：

- 工作空间（Workspace）
- 项目（Project）
- 任务（Task）
- 执行（Execution）
- 文件（File）
- 成果物（Artifact）
- 对话（Conversation）
- 提示词（Prompt）
- 技能（Skill）
- 工作流（Workflow）
- 工具（Tool）

不要仅为了简化实现而合并这些概念，除非同时说明其后果。

## 12.3 实现之前先解释

对于重要的实现任务：

1. 解释正在解决的问题。
2. 描述拟采用的方法。
3. 指出相关模块与接口。
4. 说明备选方案与权衡取舍。
5. 当变更影响架构或产品行为时，等待用户同意。
6. 增量式实现。

不要静默地做出重大架构决策。

## 12.4 教学，而非仅仅生成代码

项目开发者同时也在学习 AI 工程与软件架构。

编码 Agent 应：

- 解释不熟悉的概念。
- 解释某项实现为何如此设计。
- 指出重要的抽象与依赖关系。
- 审查代码质量。
- 解释错误与调试思路。
- 鼓励开发者对重要设计选择进行推理思考。

避免产出大量代码却不帮助开发者理解它们。

对于以学习为导向的任务，优先采用增量实现与代码审查。

## 12.5 维护工程文档

项目应逐步维护以下文档：

- `PRODUCT_SPEC.md`：产品定义与需求。
- `ARCHITECTURE.md`：系统架构与模块职责。
- `TECHNICAL_DECISIONS.md`：重要的技术决策与权衡。
- `CHANGELOG.md`：项目的重要变更。
- `LEARNING_NOTES.md`：开发过程中学到的重要工程概念。
- `TESTING.md`：测试策略与验证记录。

当架构、产品行为或重要接口发生变化时，更新相关文档。

## 12.6 工程质量

优先关注：

- 清晰的模块职责。
- 显式的接口。
- 在适当位置进行类型与数据校验。
- 错误处理。
- 日志与可观测性。
- 自动化测试。
- 安全与权限边界。
- 可维护性。

避免不必要的抽象与过早优化。

# 13. 当前产品决策与未决问题

以下决策已通过产品讨论确立。

| 领域 | 当前决策 |
|---|---|
| 产品身份 | 个人 AI 工作空间 |
| 产品名称 | mousehole |

| 模型策略 | 以 API 密钥接入云端模型为主 |

| 初始目标 | 个人用户 |

以下议题仍需要详细设计：

1. 确切的首页与工作空间内部布局。
2. 详细的任务与执行状态模型。
3. 文件元数据、引用、版本化与删除行为。

这些并不是无限期推迟开发的理由。它们应在设计相关模块时逐步解决。

# 14. 长期愿景

mousehole 应通过持续使用而变得更有用。

其价值应通过以下方面不断累积：

- 不断增长的个人知识。
- 日益有序的项目。
- 可复用的技能与工作流。
- 对任务上下文更好的理解。
- 历史执行记录。
- 不断积累的成果物。
- 持续改进的集成。

用户应逐步减少在重复指令、整理零散信息和手动协调重复工作上花费的时间。

长期目标并非仅仅是构建一个更强大的 Agent。

而是构建一个工作环境，使用户的信息、方法、工具与 AI 能力逐步融合为一个愈发一致的系统。

**最终原则：**

> mousehole 不应仅仅帮助用户完成单个任务，而应帮助用户构建一种更好的工作方式。
