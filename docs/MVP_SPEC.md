# mousehole — MVP Specification

**文档版本：** v0.1  
**阶段：** Pre-development  
**状态：** MVP 范围已确认  
**产品名称：** mousehole

---

## 1. 产品定位

mousehole 是一个面向个人用户的 Local-first AI Workspace。

它不是一个简单的 AI Chat 客户端，也不是一个单纯的 Agent 搭建平台。

它的核心目标是：

> 为用户提供一个持续存在、能够积累上下文和工作成果的个人 AI 工作空间，帮助用户组织资料、管理任务、调用 AI 能力、完成工作，并将成果沉淀下来供未来复用。

mousehole 不要求所有工作都由自身完成。它可以独立处理常见资料和知识工作，也应当具备未来连接外部 Agent、IDE、Git、MCP 等专业工具的能力。

### 1.1 核心工作闭环

Information → Understanding → Execution → Artifacts → Accumulated Workspace

具体表现为：

1. 用户将资料和信息放入工作空间。
2. 用户创建 Project 或 Task，明确工作目标。
3. mousehole 根据任务和资料组织 AI 上下文。
4. AI 执行任务，记录执行过程。
5. 生成独立 Artifact。
6. 用户可以在未来的任务中重新使用这些资料和成果。

### 1.2 MVP 要验证的核心价值

MVP 需要验证：

**用户能否在一个持续存在的工作环境中，组织多个项目和任务，引用多份资料，借助 AI 完成实际工作，并保存成果以便未来继续使用？**

MVP 不以 Agent 自主程度、工具数量或复杂度作为成功标准。

---

## 2. MVP 总体策略

采用：

**通用工作空间底座 + 一个完整业务场景。**

底座需要具备可扩展性，但首个业务场景保持简单。

### 2.1 通用底座

MVP 必须建立以下核心能力：

- Workspace
- Project
- Task
- File
- Conversation
- Execution
- Artifact
- AI Model 接入

### 2.2 首个业务场景

**多文档技术资料分析。**

典型流程：

1. 用户创建一个 Project，例如 `Agent Learning`。
2. 用户上传多份 PDF、Markdown 或 TXT 文件。
3. 用户创建 Task，例如「分析这些资料中的 Agent 架构，并整理核心概念」。
4. 用户将多份资料关联到该 Task。
5. mousehole 读取和处理资料，组织 AI 上下文。
6. 调用用户配置的模型完成分析。
7. 生成独立的分析报告 Artifact。
8. 用户可以重新打开 Project，查看资料、任务、执行记录和报告。
9. 用户可以基于之前的成果创建新任务。

MVP 应完整打通上述流程，而不是只完成一次文件上传和模型问答。

## 3. 核心概念与对象

### 3.1 Workspace

长期工作的组织环境。

MVP 至少包含：

- Global Workspace：默认工作环境，承载临时任务、通用资料和跨项目工作。
- Project Workspace：围绕具体 Project 组织的工作环境。

Workspace 不等同于 Project。用户不应被迫为每个临时任务创建项目。

### 3.2 Project

长期工作的组织单元。

基本能力：

- 创建 Project。
- 编辑名称和描述。
- 查看 Project 详情。
- 查看关联的 Task、File 和 Artifact。
- 归档 Project。

Project 用于保存长期上下文，但不要求 MVP 实现复杂的项目管理功能。

### 3.3 Task

一个具有明确目标的工作单元。

Task 不等于 Conversation。

基本能力：

- 创建 Task。
- 设置标题和任务描述。
- 关联 Project 或 Global Workspace。
- 引用一份或多份 File。
- 启动 AI 执行。
- 查看执行状态和结果。
- 查看关联的 Conversation 和 Artifact。

一个 Task 可以拥有多次 Execution，也可以产生多个 Artifact。

### 3.4 Execution

Task 的一次具体执行。

Execution 用于记录：

- 执行状态。
- 开始时间和结束时间。
- 使用的模型。
- 执行结果。
- 错误信息。
- 执行结果摘要。

建议至少支持：

- Pending
- Running
- Completed
- Failed
- Cancelled（如果实现取消机制）

Task 与 Execution 必须分离。重新执行一个任务时，应产生新的 Execution，而不是覆盖旧执行记录。

### 3.5 File

用户上传的原始资料。

采用统一 Global Library 的文件组织思路：

- 文件实际存储在统一文件库中。
- Project 和 Task 通过引用使用文件。
- 一个文件可以被多个 Project 或 Task 引用。
- 文件的物理存储位置与使用范围分离。
- 上传到 Global Library 不意味着所有任务都能自动读取该文件。

MVP 支持上传、列表查看、读取、删除和关联。

删除文件时，需要考虑其是否仍被其他 Project 或 Task 引用，避免意外破坏已有工作。

### 3.6 Conversation

保存用户与 AI 在任务执行过程中的对话。

Conversation 可以关联 Task，也可以作为工作过程的记录。

但 Conversation 不是成果的唯一存储形式。

### 3.7 Artifact

AI 或用户产生的独立工作成果。

例如：

- 技术文档分析报告。
- 学习总结。
- 多份资料的综合分析。
- 技术方案说明。

Artifact 必须能够独立查看，并与对应的 Project、Task 和 Execution 建立关联。

MVP 至少支持：

- 生成并保存 Artifact。
- 查看 Artifact。
- 查看其来源 Task。
- 在 Project 中找到相关 Artifact。

编辑、版本管理和导出可以放在后续迭代。

## 4. 功能需求与优先级

### 4.1 Workspace

**P0：**

- 默认 Global Workspace。
- 首页展示基本工作信息。
- 能够进入 Project。
- 提供明显的新建 Task 入口。

**P1：**

- Workspace 个性化配置。
- Project 模板。

### 4.2 Project

**P0：**

- 创建、查看、编辑和归档 Project。
- Project 详情页。
- 展示关联文件、任务和成果。

### 4.3 Task

**P0：**

- 创建 Task。
- 设置任务标题和描述。
- 关联 Workspace 或 Project。
- 引用多份资料。
- 查看 Task 详情和状态。
- 启动 AI 执行。

**P1：**

- 重新执行。
- 选择基础 Prompt 模板。
- 更灵活的任务上下文配置。
- Task 之间的关联。

### 4.4 File

**P0：**

- 上传文件。
- 文件列表。
- 文件基本信息。
- 文件解析。
- 文件与 Project、Task 的关联。
- 文件读取和删除。

**P1：**

- 标签。
- 文件版本。
- 更丰富的文件预览。

### 4.5 AI Runtime

**P0：**

- 配置至少一种云端模型服务。
- 保存模型配置。
- 使用 API Key 调用模型。
- 将任务描述、Prompt 和资料上下文组织为模型输入。
- 接收模型响应。
- 处理 API 调用失败和超时。
- 将结果交给 Artifact 系统保存。

模型接入应尽量与业务逻辑解耦，避免 Task 或文件处理代码直接依赖某个模型供应商的专有接口。

**P1：**

- 多模型管理。
- 不同任务选择不同模型。
- 模型调用策略。

### 4.6 Execution

**P0：**

- 每次任务执行创建独立 Execution。
- 记录执行状态。
- 记录开始和结束时间。
- 记录使用的模型。
- 保存执行结果和错误信息。

**P1：**

- 更详细的步骤追踪（ExecutionStep 持久化与回放）。
- 重试策略。
- Token 用量和成本统计（MVP 已记录 Provider 返回的 usage，统计报表为 P1）。

### 4.7 Artifact

**P0：**

- 保存 AI 生成的成果。
- 独立查看成果。
- 关联 Project、Task 和 Execution。
- 在 Project 中展示成果列表。

**P1：**

- 编辑。
- 版本管理。
- Markdown、PDF 等格式导出。

### 4.8 Conversation

**P0：**

- 保存用户与 AI 的基本交互记录。
- 能够查看任务相关对话。

**P1：**

- 在已有任务中继续对话。
- 从已有 Artifact 或 Conversation 创建后续任务。

### 4.9 Capability

基础 Prompt 模板机制属于 P1，不是 MVP 必交内容。

MVP 中 Task 使用内置系统提示词完成任务执行，不强制选择模板；模板选择与模板 CRUD 留待后续迭代。

后续建议提供少量初始模板：

- 技术文档分析。
- 多文档综合总结。
- 概念解释。
- 学习报告生成。

模板应支持用户选择，并允许提供任务额外指令。

完整 Skill、Workflow、能力推荐和能力导入不属于 MVP 必须实现的内容。

### 4.10 Integration

**P0：**

- 基础模型 API 接入。

**P1：**

- MCP。
- GitHub。
- IDE。
- 外部 Agent。

## 5. 多文档处理与上下文检索

这是 MVP 的重要业务能力。

### 5.1 文件格式

MVP 必须支持：

- PDF
- Markdown
- TXT

暂不支持：

- Word
- Excel
- PowerPoint
- 图片 OCR
- 音视频

不支持的文件格式必须明确提示，不允许静默忽略。

### 5.2 多文件引用

一个 Task 可以引用多份资料。

文件引用应当独立于文件的物理存储。

同一份文件可以被多个 Task 使用，也可以被多个 Project 引用。

AI 执行时，只能读取当前 Task 明确授权或关联的文件，以及该任务明确允许使用的其他上下文。

不能因为某个文件存在于 Global Library，就自动将其内容暴露给所有任务。

### 5.3 渐进式上下文检索

采用渐进式检索策略：

**第一阶段：直接检索（MVP 实现）**

- 获取当前 Task 引用的文件。
- 提取文件文本。
- 进行必要的文本清洗。
- 对内容进行分段和组织。
- 根据上下文预算决定输入模型的内容。
- 必要时进行分批处理和中间摘要。
- 将整理后的上下文交给模型完成任务。

注意：直接检索不等于无条件将所有文件全文拼接进 Prompt。

必须考虑模型上下文长度、Token 预算、文件数量和文件大小。

当资料规模超出可处理范围时，应给出明确提示，或使用分批处理和摘要汇总策略。

**第二阶段：RAG（后续扩展）**

未来引入：

- Embedding。
- 文本切片与索引。
- 向量检索。
- 混合检索。
- 重排序。
- 检索结果增强生成。

长期方向是根据任务需求和资料规模，选择直接读取或 RAG 检索。

MVP 不需要实现自动检索策略判断，也不需要提前建设完整向量数据库系统。

但文件处理、上下文组织和检索逻辑应保持模块化，避免未来增加 RAG 时推翻现有核心数据模型。

## 6. 部署与数据安全

### 6.1 部署形态

MVP 采用单用户、本地部署优先。

- 应用运行在用户自己的电脑或自管服务器。
- 数据库存储在用户控制的环境中。
- 用户文件存储在本地或自管存储中。
- AI 模型通过云端 API 调用。
- 暂不实现 SaaS 多租户和多人协作。

Local-first 不代表完全离线。

### 6.2 模型与 API Key

- 支持用户配置模型 API Key。
- API Key 不应明文暴露在前端。
- 不应将 API Key 写入普通日志。
- 不应将密钥提交到代码仓库。
- 应明确模型服务提供方和数据发送边界。

### 6.3 执行安全

MVP 以受控只读操作为主：

- 读取用户明确关联的文件。
- 调用模型 API。
- 保存 AI 生成的 Artifact。
- 记录执行信息。

不开放任意 Shell 执行。
不开放未经授权的文件覆盖。
不开放未经确认的外部写操作。

未来加入具有副作用的工具时，必须在执行层实现权限检查和必要的人工审批，不能只依赖 Prompt 中的安全指令。

## 7. MVP 非目标

以下内容明确不属于第一版开发范围：

1. 多 Agent 自主协作平台。
2. 复杂 Workflow 可视化编排。
3. 完整 Skill 市场。
4. 自动 Skill 进化。
5. 完整 MCP 管理中心。
6. VS Code 插件。
7. GitHub 深度集成。
8. 复杂 RAG 知识库系统。
9. 企业级多租户和 RBAC。
10. 多人实时协作。
11. 完整离线模型管理。
12. 复杂任务依赖图。
13. 任意 Shell 和高权限工具执行。

这些功能并非与 mousehole 的愿景冲突，而是为了控制 MVP 的开发成本，暂时不实现。

## 8. MVP 验收标准

MVP 不是以页面数量或代码规模验收，而是以端到端工作闭环验收。

### 8.1 工作空间

- [ ] 用户打开应用后可以进入 Global Workspace。
- [ ] 用户可以创建和查看 Project。
- [ ] 用户可以从工作台进入 Project。
- [ ] 用户可以创建临时 Task，而不必创建 Project。

### 8.2 文件管理

- [ ] 用户可以上传 PDF、Markdown 和 TXT 文件。
- [ ] 用户可以查看文件列表和基本信息。
- [ ] 系统能够正确解析支持的文件。
- [ ] 不支持的格式能够给出明确错误。
- [ ] 一个 Task 可以关联多份文件。
- [ ] 同一个文件可以被多个 Task 引用。

### 8.3 AI 执行

- [ ] 用户可以配置云端模型。
- [ ] 用户可以创建多文档分析任务。
- [ ] 系统能够读取 Task 关联的文件。
- [ ] 系统能够组织多份资料的上下文。
- [ ] 系统能够处理基本的上下文预算问题。
- [ ] 系统能够调用模型并接收响应。
- [ ] 模型调用失败时能够显示明确错误。

### 8.4 执行记录

- [ ] 每次执行创建独立 Execution。
- [ ] 用户能够查看执行状态。
- [ ] 用户能够查看基本执行结果。
- [ ] 用户能够查看执行失败信息。

### 8.5 成果沉淀

- [ ] AI 生成的成果可以保存为 Artifact。
- [ ] Artifact 可以独立查看。
- [ ] Artifact 能够关联对应的 Task 和 Project。
- [ ] 用户重新打开 Project 后能够找到之前的资料、任务和成果。

### 8.6 核心场景验收

使用真实的多份技术资料完成一次完整工作：

1. 创建 `Agent Learning` Project。
2. 上传至少两份技术资料。
3. 创建一个多文档分析 Task。
4. 将两份资料关联到 Task。
5. 调用云端模型执行分析。
6. 生成一份结构化报告。
7. 将报告保存为 Artifact。
8. 退出并重新进入应用。
9. 再次进入 Project，能够找到原来的资料、Task 和 Artifact。

**以上完整流程成功，才算 MVP 核心场景通过验收。**

## 9. 开发原则

后续开发 Agent 必须遵循：

1. 优先保证核心数据模型和业务关系清晰。
2. 不要为了展示功能而构建大量没有实际作用的模块。
3. 不要在 MVP 阶段提前实现复杂 Agent 架构。
4. 不要将 Conversation 当成唯一的工作记录和成果存储方式。
5. 不要将 File 与 Project 或 Task 进行强绑定。
6. 不要将业务逻辑与单一模型供应商深度耦合。
7. 文件处理、上下文组织和 AI 执行应保持合理的模块边界。
8. 所有重要执行应当有可追踪记录。
9. 错误应当明确呈现，不能静默失败。
10. 优先采用成熟、简单、可维护的技术方案。
11. 不要为了未来可能出现的需求过度设计。
12. 对尚未确定的技术细节，先提出方案和权衡，不要擅自扩大 MVP 范围。

**文档结论：**

mousehole MVP 的目标不是成为一个功能丰富的 AI Agent 平台，而是建立一个真正可用、能够持续积累工作上下文的个人 AI 工作空间。

第一版必须完整实现：

**组织工作 → 创建任务 → 引用多份资料 → AI 分析 → 保存成果 → 未来继续使用。**

其他能力围绕这个闭环逐步扩展。
